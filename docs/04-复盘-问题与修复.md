# 复盘：五个真实问题与修复过程

这一页只写**确实发生过、并且能指出证据**的问题。
每条都分清"已验证"和"仍未解决"，不把推测写成结论。

## 问题一：v2 结尾选错了镜头

### 现象

v2 成片结尾有一段约 2 秒的**白色遥控器满屏、屏内全黑**的画面，观众看到的是"一块什么都没有的黑屏"。
这片子在初次验收时被指出来，才回去查。

### 原因

v2 的剪辑表是按**秒数区间**从 S1 里切片的，而 S1 的内部镜序和预设的不一样。
原以为：

- `S1 2.6–5.2` = 纯海景
- `S1 7.0–7.9` = 纯仰头镜头

逐帧复核 `S1_v1.mp4` 后的真实镜序是：

| S1 时间 | 实际内容 |
|---|---|
| 0.00–2.05 | 港口海面大全景，**无人物** |
| 2.10–5.50 | 岸桥下人物侧身/背影 |
| **5.75–6.50** | **白色遥控器满屏、屏内全黑** |
| 7.00–约 14.50 | 白色遥控器满屏、屏内有港口画面 |
| 14.40–15.80 | 遥控器屏幕近景收尾（屏内是桁架上的模糊人影） |
| **15.90–19.80** | **人物侧背影连续镜头**（遥控器只占握持小面积、屏幕朝内不可见） |

所以 v2 切到的两个"以为"的区间，一个是黑屏特写，一个是岸桥背影。

### 修复

换素材，不重生成：

```
SEG6 = S1 16.60–19.50（人物侧背影 2.90s）  →  S1 0.10–2.05（纯海面 1.95s）  →  渐黑
```

### 结论（已验证）

- 84.792–87.667s 为人物侧背影，遥控器小面积、屏朝内，**无满屏白遥控器**
- 87.667s 起为纯海面，**无人物**
- 89.542s 起全黑（`blackdetect` + 逐帧 Y 均值双证）

### 代价

S1 里的纯海面只有 1.95 秒可用，没有生成新素材、没有插帧补时长。
所以结尾海面只能亮 0.75 秒就开始渐黑——这是素材决定的，不是剪辑偏好。

## 问题二：遥控器造型不统一（未解决）

### 现象

- S1、S2 里是**白色**带屏遥控器
- S3、S4 里是**深灰/黑色**机身

同一个角色、同一场戏，手里的东西变了。

### 原因

四段是分别生成的，每段的参考图不同，模型对"同一台遥控器"的理解不一致。
S3/S4 的参考图来自上一段末帧，但末帧里遥控器只占很小面积，模型自己补成了深色。

### 处理（部分规避，未真正解决）

不是修复，是**绕过去**：

1. 剪辑时优先选**遥控器在画面中占比小**的镜头
2. 屏幕内容多的镜头，只切屏幕局部，不露全机身
3. 结尾用背影，遥控器基本不可见

### 结论（仍未解决）

**遥控器造型不统一没有被消除**，只是被压缩到了观众不容易注意的程度。
真正解决需要重新生成 S1/S2 或重新生成 S3/S4，成本是 2 条视频生成额度，本次没做。

## 问题三：concat 输出映射遗漏，计帧脚本假成功

### 现象

为了核对 47 个分片到底占多少帧，写了一个测量脚本：把每个分片单独 trim 出来，
concat 成一条"只有画面"的流，再数帧。

脚本跑完返回退出码 0，但**输出目录里一个分片文件都没有**。

### 原因

滤镜图里 concat 的输出标签叫 `[outv]`，但 `-map` 参数忘了写。
ffmpeg 在**绑定阶段**就拒绝执行：

```
Filter 'concat:out:v0' has output 0 (outv) unconnected
```

而脚本没有检查 `returncode`，只看了"进程结束"，于是把一个失败当成了成功，
后续所有基于这个"成功"结果的推算全是空的。

### 修复

两件事一起改：

1. 显式 `-map "[outv]"`，把输出接上
2. **任何一次调用失败都抛错并保存 stderr，绝不返回估计值**

```python
if r.returncode != 0 or not m:
    raise SystemExit("计帧失败：%s ..." % ...)
```

### 教训

这是整个项目里最贵的一次教训：**退出码 0 不等于做完了**。
要验证的是"该产出的东西是否真的存在"，不是"命令有没有报错"。

## 问题四：音视频计时差异（部分定位）

### 现象

47 个分片按帧累加，应该得到 2146 帧。但成片总长和分片位置都有轻微偏移：

- 按帧累计 SEG6 应该落在 `84.583s`
- 成片实测 SEG6 落在 **`84.792s`**

差 0.209 秒 ≈ 5 帧。

### 已验证的部分

实测 47 段后：

| 指标 | 数值 |
|---|---|
| 分片帧数 | 2146 帧 |
| `sum(视频段)` | 89.416669s |
| `sum(max(视频段, 音频段))` | 89.641667s |
| 差值 | **+0.225s ≈ 5.4 帧** |

`sum(max)` 比 `sum(视频段)` 多出来的部分，正好对上实测偏移的量级。

**成因**：`concat` 滤镜按段拼接时，每段的占位不是"视频段长度"，而是
**max(视频段, 音频段)**。视频段是按整帧向下取整的（`trim` + `setpts` 之后帧数固定），
音频段是精确的秒数（`atrim` 之后按采样点计算）。两者在每个分片上都有零点几帧的差，
47 段累计起来就是 0.2 秒。

### 仍未解决的部分

`sum(max) − 2146/24 = 0.225s`，但实测偏移是 `0.209s`，**还差约 2 帧（0.125s）无法解释**。

可能的方向（未验证，不作为结论）：

- `concat` 内部对音频的重采样与 `aresample=48000:async=1` 的时序交互
- 某些分片的音频段比视频段短，`max` 取了视频段，与上表的估算方向相反
- 帧率相关的时间基在 `-r 24` 输出时的取整

**所以这一节的结论只写到"主因是 max(视频段, 音频段) 占位，仍有 2 帧未定位"。**
不写"完全解释"，因为没解释完。

### 实际影响

成片本身没有因此出错。因为字幕窗不是按帧累计算的，而是**按成片实测切点锚定**的
（84.85 / 87.45 这两个值是抽帧量出来的，不是算出来的）。

这也是那次复盘的真正结论：**不要用推算值排字幕，要用实测值。**

## 问题五：结尾渐黑吃掉了整个海面段

### 现象

v2.1 的第一版里，结尾本该有 1.95 秒的纯海面，实际只剩约 0.1 秒就黑了。

### 原因

渐黑是用「画面总长 − 1.40s」倒推起点：

```
fade=t=out:st=<总长 - 1.40>:d=1.15
```

但"总长"是 47 个分片 + 4 秒尾部黑场堆出来的，而 fade 是挂在**整条已 concat 的流**上的。
倒推出来的起点正好落在海面段的前面，把 1.95 秒的海面从一开始就压黑了。

### 修复

把 fade 挂到**海面分片自己的 filter 链**上：

```
scale=1280:720:flags=lanczos,setsar=1,fade=t=out:st=0.75:d=1.15
```

这里的 `st=0.75` 是相对这一片自己的时间线（从它开始算 0.75 秒），
不是全片时间。所以无论前面怎么堆，海面一定先亮 0.75 秒，再用 1.15 秒渐黑。

### 结论（已验证）

- 87.667s 起海面亮起
- 88.420s 开始渐黑
- 89.542s 全黑（Y<4）
- 海面可见时长约 0.75 秒 + 渐黑 1.15 秒

## 附二：抽帧核对的 seek 写错，会得出完全错误的结论

### 现象

核对"人物侧背影 → 纯海面"的切点时，用 `-ss 87.45` 抽帧，
图上显示**已经是海面**，据此差点把时间线改成"87.45 切海面"。

换个精度再抽同一时刻，同一位置又是**人物侧背影**。同一份文件、接近的时间点，两张图内容相反。

### 原因

```
错误：ffmpeg -ss 87.450 -i in.mp4 -frames:v 1 out.png    # 快速 seek，吸附关键帧
正确：ffmpeg -i in.mp4 -ss 87.450 -frames:v 1 out.png    # 精确 seek，逐帧解码丢弃
```

`-ss` 放在 `-i` 之前是 input seeking，它会跳到最近的**关键帧**再解码，
精度取决于关键帧密度。在关键帧间隔大的编码上，取到的帧可能和请求时间差好几秒。

### 修复

`sub_edge_check.py` 改为 `-ss` 放在 `-i` 之后（精确 seek），时间精度提到 0.0001 秒。

### 实测复核（精确 seek 后）

| 时间 | 画面 | 结论 |
|---|---|---|
| 87.625 | 人物侧背影 | 切点仍未到 |
| **87.667** | **纯海面** | **切点确认在 87.625–87.667 之间** |
| 88.375 | 海面，正常亮度 | 渐黑未开始 |
| **88.417** | **海面明显变暗** | **渐黑开始 ≈ 88.42** |
| **89.542** | **全黑** | **黑场起点确认** |
| 89.583 / 89.625 | 全黑 | — |

三条时间码全部成立：**87.667 切海面 / 88.42 渐黑 / 89.542 全黑**。
之前那份"87.45 就是海面"的结论是 seek 误差造成的假象。

### 教训

**核验工具本身也会骗人。** 拿一张抽帧图当证据之前，先确认这张图是不是你请求的那一帧。
这不是理论问题——它差点让一版已经正确的剪辑被"修正"成错的。

## 附三：字幕层整层丢失（静默失败）

在字幕层生成阶段还遇到一个问题：用 PIL 画"阴影 + 正字"两层时，
`alpha_composite` 之后继续用**合成前创建的 `ImageDraw` 对象**画正字，
结果正字没有落到图上——**整层透明**，但脚本照样打印出文件大小和 alpha 值。

修复：

```python
sh = sh.filter(ImageFilter.GaussianBlur(sh_blur))
layer = Image.alpha_composite(layer, sh)
draw_text(ImageDraw.Draw(layer), color + (255,))   # 必须重新 ImageDraw.Draw
```

判断是否真的画上了，不能看文件大小，要看 `layer.getextrema()[3][1]`
（alpha 通道最大值），以及最终成片底部裁带的抽帧。
